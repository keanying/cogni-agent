2.7提问-发起提问POST/api/app/chat唯一的发起入口。点问题树里的问题就传 issue_id;自由提问就传 message + 目标。返回 task_id,拿它订阅事件流。

1 开始

1.1 三步跑通第一个请求

  1. 先看清自己要接哪一块:移动端/小程序 → 第 2 章(账号登录);管理后台页面 → 第 3 章(账号登录); 外部系统集成 → 第 4 章(API Key)。三块的鉴权方式不同,别混用。
  2. 拿凭证:外部集成在管理后台「工具中心 · API Key」创建,形如 sk-zhilv-xxxxxxxx(只显示一次); 前端/管理端用账号登录换 access_token。
  3. 发请求:把下面这段里的 https://your-host 和 Key 换成你的,直接粘进终端。
最小可用请求
1curl --location --request POST 'https://your-host/v1/quickbi/query' \
2--header 'Authorization: Bearer sk-zhilv-xxxxxxxx' \
3--header 'Content-Type: application/json' \
4--data-raw '{
5 "question": "本月各平台销售额",
6 "target": { "cube_id": "abc123" }
7}'
没有 cube_id 也能问:不传 target 时平台按该 Key 所属景区自动挑已登记的数据。 先调一次「目录」接口看看这个景区有什么,是最省事的起手式。

1.2 服务地址与通用约定

面向谁前缀鉴权本文档章节
移动端 / 小程序/api/app/*账号登录(JWT)第 2 章 前端 APP
管理后台页面/api/admin/*账号登录(JWT)第 3 章 管理后端
外部系统集成/v1/*API Key第 4 章 Quick BI 与开放平台
健康检查/health无—
交互式接口清单/docs无—
  • 请求体一律 JSON(Content-Type: application/json);只有文件上传用 multipart/form-data。
  • 每个响应都带 X-Trace-Id 响应头。出问题时把这个值发给平台运维, 能直接定位到那一次调用的完整链路;也可以自己在请求头传 X-Trace-Id,平台会沿用。
  • 流式用 SSE(text/event-stream),不是 WebSocket;请求体里加 "stream": true 开启(APP 端是单独的订阅端点)。

1.3 鉴权一:API Key(外部集成)

所有 /v1/* 接口统一用这一个请求头:

请求头
1Authorization: Bearer sk-zhilv-xxxxxxxx

Key 的两个属性,直接决定你能看到什么

属性含义
所属景区景区级 Key 只能看到本景区 + 集团级的连接、资产与固定问题;集团级 Key(未绑景区)能看到全部。
限定 Agent限定了可调用 Agent 的 Key 不能调用 Quick BI 开放接口(返回 403)。 要用 Quick BI,请用未限定 Agent 的 Key。
多租户场景可以额外传 X-End-User: <你的终端用户标识>, 平台会把这次调用归到该终端用户名下,便于分摊成本与排查。

1.4 鉴权二:账号登录(前端 / 管理后台)

/api/app/* 与 /api/admin/* 用账号登录换来的令牌:

请求头
1Authorization: Bearer <access_token>
  1. 取 RSA 公钥(免登录),用它加密密码 —— 明文密码不要过网。
  2. 调登录接口拿 access_token + refresh_token。
  3. access_token 过期前用 refresh_token 换新的;两个令牌都会滚动更新。
must_change_password=true 时必须先改密码,否则后续接口会一直被拦。 这是首次登录与管理员重置密码后的状态。

1.5 响应信封与错误码

所有非流式 JSON 响应都包一层信封,业务数据在 data 里:

响应信封
1{
2 "code": 0,
3 "message": "success",
4 "data": { ... },
5 "trace_id": "b6289ec8..."
6}
序号字段类型示例注释
1codeint00 = 成功,非 0 = 失败
2messagestringsuccess失败时是可直接展示给人看的中文原因
3dataobject / array{…}业务数据
4trace_idstringb6289ec8…追踪 ID,与响应头 X-Trace-Id 一致
写客户端时请只判断 code,不要只看 HTTP 状态码;并且永远记录 trace_id —— 排查时它比任何日志都管用。

错误码

HTTP典型 message怎么处理
401API Key 无效 / 已吊销 / 已过期;或令牌过期换有效 Key;账号登录场景用 refresh_token 换新令牌
403该 API Key 限定了可调用的 AgentQuick BI 请用未限定 Agent 的 Key

1.6 SSE 事件结构

所有流式接口都推这套事件。事件名就是 JSON 里的 type,一行 data: 一个 JSON 对象:

事件流
1event: run
2data: {"type":"run","run_id":"run_7c1f2b9d","capability":"dataset_qa"}
3 
4event: stage
5data: {"type":"status","message":"正在选择数据集…","channel":"thinking"}
6 
7event: text
8data: {"type":"text","delta":"本月各平台销售额合计 386.2 万元","channel":"data"}
9 
10event: chart
11data: {"type":"chart","channel":"data","chart":{"title":"各平台销售额","chart_type":"bar",
12 "columns":["平台","销售额"],"rows":[["抖音",1203560]]}}
13 
14event: done
15data: {"type":"done","run_id":"run_7c1f2b9d","status":"success","answer":"…","duration_ms":4210}
事件channel含义与怎么渲染
run—本次运行开始,带 run_id。先存下来:后面查结果、对账都靠它
stagethinking过程信息(选表、生成 SQL、执行中)。渲染成「正在思考」那类提示,不要当回答
token / textdata回答正文,按 delta 追加拼接(APP 端叫 token,开放平台叫 text)
chart / structureddata图表:开放平台给原始 chart,APP 端给渲染好的 ECharts option
reportdata报告链接(报告类才有)
usage—本次 token 用量
done—结束。status = success / failed,失败时 error 是原因
error—致命错误,流随即结束
