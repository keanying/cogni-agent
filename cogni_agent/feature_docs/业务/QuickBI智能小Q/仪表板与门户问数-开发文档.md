## 0. 术语与约定

| 术语 | 含义 |
|---|---|
| 连接(connection) | 一套 Quick BI 凭证:`server_domain` + `api_key`(AccessId)+ `api_secret`(AccessKey)+ `user_token`(Quick BI 用户 ID,**决定能看到哪些数据**)。所有远端 id(pageId、cubeId、fileId)只在它所属的那条连接下有效。 |
| 仪表板(dashboard) | Quick BI 仪表板,远端主键 `pageId`(也叫 worksId / dashboardId / treeId)。 |
| 数据门户(data portal) | Quick BI 数据门户,地址带 `productId` + 可选 `menuId`;菜单节点挂着一块仪表板,需要按菜单树解析出 pageId。 |
| 数据集(cube) | Quick BI 数据集,远端主键 `cubeId`。仪表板的每个图表组件引用一个数据集(`dataFromId` / `queryInput.sourceId`)。 |
| 资产(asset) | 平台侧登记的仪表板 / 数据集,表 `tc_qbi_assets`。仪表板资产缓存了结构摘要(`meta`)。 |
| 固定问题(fixed question / issue) | 统一问题表 `scenic_agent_issue_detail` 中 `business_class='quick_bi'` 的行。管理端叫固定问题,APP 端叫问题。 |
| 运行(run) | 一次提问的执行记录,表 `tc_qbi_runs`。**同时是加速缓存的存储**(没有单独的缓存表)。 |
| 能力(capability) | `dataset_qa` 问数·数据集 / `file_qa` 问数·上传文件 / `dashboard_qa` 报表·仪表板 / `insight` 解读 / `report` 报告 / `doc_parse` 文档解析。 |
| 快照(snapshot) | `snapshot/calling/shot` 把仪表板**当前页签**按查询控件默认值导出成 Markdown 表(官方解读的取数方式)。 |
| 补取(fill-in) | 快照没覆盖到的图表(别的页签 / 快照里只有表头),按它们的数据集再问数取一次数据。 |
| 口径说明(model_instruction) | 固定问题上运营写的约束(取哪个窗口、按什么顺序输出…)。**只给回答 / 解读用,不给选表 / 取数用**。 |
| 运行时变量 | `{{截止时间}}` `{{统计日期}}` `{{昨日}}`,每次运行按东八区当前时刻替换。 |
| 参数模板变量 | `{{today}}` `{{yesterday}}` `{{month}}` `{{last_month}}` `{{year}}` 及问题行 `param_template` 里的键,APP 发起 / 预热时按当天展开。 |
| 加速(prewarm) | 固定问题上的开关 + 刷新间隔 + 存储时长。开了之后后台按间隔预先跑,提问时在存储时长内直接回放。 |

约定:
- 所有对外错误文案用中文、说清「哪一步 / 为什么 / 下一步怎么做」。
- 「不编数」是硬约束:取不到数据就明确失败或明确说没有,**不允许**把空表 / 无关数据交给模型让它「凑一个回答」。

## 1. 总体架构与调用链

```
                 ┌──────────────────────── 前端(React)────────────────────────┐
                 │ 固定问题(TargetPicker)· 数据资产 · 操练台 · 运行记录         │
                 └──────────────┬──────────────────────────────────────────────┘
   管理端 /api/admin/quickbi/*  │      APP /api/app/chat · /api/app/quickbi/ask      开放平台 /v1/quickbi/*
                 ┌──────────────▼──────────────────────────────────────────────┐
  路由层         │ routes_admin.py      gateway_service/routes_app.py   routes_open.py │
                 │                      (+ qbi_bridge:Quick BI 事件 → APP 事件)        │
                 └──────────────┬──────────────────────────────────────────────┘
  执行层         │ service.run_stream(唯一执行入口)                              │
  (落库/鉴权/    │   固定问题带出 → 运行时变量 → 加速缓存 → 连接解析 → 景区映射       │
   缓存/收尾)    │   → 能力纠正/路由 → 拼口径 → 建运行记录 → _prepare → 事件流 → 收尾 │
                 └──────────────┬──────────────────────────────────────────────┘
  能力层         │ capabilities.py:run_dashboard_qa / run_dashboard_insight /        │
  (只依赖客户端, │   run_multi_cube_qa / run_dataset_qa / run_insight / run_report …  │
   不碰数据库)   │ dashboard.py:地址识别、门户菜单解析、结构精简解析                │
                 │ events.py:上游事件归一化、图表结构、累积器、通道标记              │
                 └──────────────┬──────────────────────────────────────────────┘
  客户端         │ client.py(httpx,SSE,信封解包)+ signing.py(X-Gw-* 签名)      │
                 └──────────────┬──────────────────────────────────────────────┘
                                ▼
                          Quick BI OpenAPI
```

分层规则(实现时必须守住):
1. **能力层不碰数据库**:输入是 `QuickBIClient` + 参数,输出是统一事件的 async generator。需要落库 / 调大模型的,用回调注入(如文档解析的 `llm` / `save_output`)。
2. **执行入口只有一个**:管理端、APP、开放平台、Agent 工具、预热任务全部走 `service.run_stream`。缓存、口径、景区、连接解析只在这里做一遍——两处各写一份迟早口径分叉(本轮最大的一类问题就是 APP 侧自己写了一套缓存)。
3. **事件协议统一**:首个事件 `run`,最后一个事件 `done`,中间是 `status / meta / reasoning / text / sql / chart / report / error …`(附录 A)。缓存回放也必须产出同形的事件。

## 2. Quick BI OpenAPI 清单

### 2.1 签名(所有请求)

请求头:`X-Gw-AccessId`、`X-Gw-Nonce`(uuid4)、`X-Gw-Timestamp`(毫秒)、`X-Gw-Signature`。

```
StringToSign = METHOD + "\n" + URI
             [+ "\n" + "k1=v1&k2=v2"]          # 参与签名的参数,按 key 升序,空值跳过,值不做 URL 编码
             + "\nX-Gw-AccessId:" + accessId
             + "\nX-Gw-Nonce:" + nonce
             + "\nX-Gw-Timestamp:" + timestamp
Signature    = Base64( HMAC-SHA256( api_secret, urlencode(StringToSign, safe="") ) )
```

- GET:query 参数参与签名;`x-www-form-urlencoded`:表单参与签名;**JSON body 不参与签名**;multipart 上传签名参数为空。
- 响应信封:`{success, code, message, data, traceId}`。`success=false` 时按 `code` 查已知错误码(§14)。

### 2.2 本链路用到的接口

| 用途 | 方法 + URI | 关键请求 | 关键响应 | 备注 |
|---|---|---|---|---|
| 可问数数据集 | GET `/openapi/v2/smartq/query/llmCubeWithThemeList` | `userId`, `runningBySkill=true` | `cubeIds` 映射 / 主题列表 | 连接自检也用它 |
| 智能选表 | POST `/openapi/v2/smartq/tableSearch` | `{userId, userQuestion, llmNameForInference:"SYSTEM_deepseek-r1-0528", runningBySkill:true, cubeIds?}` | cubeId 列表 | 批次 30→10 降级;问题**去掉口径说明**再传 |
| 单表问数(流) | POST `/openapi/v2/smartq/queryByQuestionStream`(SSE) | `{userQuestion, userId, cubeId, llmNameForData:"nvl", llmNameForInference:"nvl", runningBySkill:true, locale}` | 事件:trace / text / reasoning / sql / param(DSL)/ olapResult / finish / error | |
| 多表问数(同步) | POST `/openapi/v2/smartq/queryByQuestion` | `{userQuestion, userId, multipleCubeIds:[...]}` | 单步:顶层 olap 字段;多步:`dataList`(元素可能是 **JSON 字符串**) | **`multipleCubeIds` 必须是 JSON 数组**,逗号字符串会报 AE0510000038 |

| 数据解读(流) | POST `/openapi/v2/smartq/dataInterpretationStream` | `{stringData: base64(markdown), userQuestion: 守卫提示词+问题, oapiUserId, locale, runningBySkill:true}` | 事件:trace / locale / summary(subType=model_reasoning 是推理)/ text / finish / error | markdown 上限 100,000 字符 |
| 报告引用文件 | POST `/openapi/v2/qreport/uploadReferenceFile` | multipart | fileId / fileType | |
| 创建报告 | POST `/openapi/v2/smartq/createQreportChat` | `{userQuestion, needWebSearch, attachment(JSON 串,内含 useOnlineSearch), resources, ...}` | chatId | 同一账号同时只允许一个运行中的报告 |
| 报告进度 | POST `/openapi/v2/smartq/qreportChatData` | chatId | 事件串 | |

### 2.3 客户端要求

- 超时:普通请求 60s,SSE 600s(可配)。
- SSE 解析兼容 `\n` / `\r\n` 分隔;`finish` 之后的事件丢弃。
- 每次请求留痕(请求体脱敏、响应原文限长),运行记录里可一键导出「执行详情」——现场排障全靠它(§17 的所有结论都来自导出)。

## 4. 仪表板 / 数据门户:识别、解析、登记

### 4.1 地址识别(`dashboard.py`)

`_ID = [a-zA-Z0-9\-_]+`

| 输入 | 判定 | 提取 |
|---|---|---|
| `https://bi.aliyun.com/dashboard/view/pc.htm?pageId=xxx` | 仪表板 | `pageId=(_ID)` |
| `https://bi.aliyuncs.com/token3rd/dashboard/view/pc.htm?pageId=xxx&accessTicket=...` | 仪表板(嵌入) | 同上;`accessTicket` 只用于展示 / 回跳,OpenAPI 不用 |
| `https://bi.aliyun.com/product/view.htm?productId=xxx&menuId=yyy` | 数据门户(含 `/product/view.htm`) | `productId=(_ID)`(必需),`menuId=(_ID)`(可选) |
| 纯 `_ID` | pageId | 原样 |
| 其它 | — | `ValueError("无法从地址中提取 pageId:…")` → 输入错误 |

标准查看地址:`{server_domain}/dashboard/view/pc.htm?pageId={pageId}`(写进 `meta.view_url`)。

### 4.2 数据门户 → pageId(`resolve_page`)

1. GET `dataportal/query?dataPortalId=productId`;`menu` 或 `menus`(dict 包成 list);空 → 「数据门户没有配置任何菜单」。
2. 选菜单 `select_menu(menus, menuId)`:
   - 给了 menuId:深度优先找 `id == menuId`;找不到 → 「数据门户中找不到菜单 {menuId}」。
   - 没给:先找 `isHome` 菜单,在它下面找**第一个可用叶子**;没有则在整棵树里找。
   - 「可用叶子」`_find_first_child`:非空(`isEmpty` 假)、未隐藏(`pcConfig.isHide` 假)、无子节点、`content[0].type` 存在且 ≠ `url`;隐藏或无子节点的分支直接跳过。
3. `page_id_from_menu(menu)`:`content[0]`
   - 没有 content → 「菜单没有关联任何内容」;
   - `type != "report"` → 「该菜单关联的是「{类型中文名}」({名称}),不是仪表板,请提供指向仪表板的数据门户链接」(类型中文名表:report 仪表板 / excel 电子表格 / url 外部链接 / page 页面 / form 数据填报 / download 自助取数 / Cube 数据集 / analysis 即席分析 / screen 数据大屏);
   - 无 id → 「菜单「{名称}」未关联有效的仪表板 ID」。
4. 返回 `{page_id, name, portal: {product_id, menu_id, portal_name, menu_title}}`。`portal` 写进资产 `meta.portal`,列表 / 下拉据此显示「门户名 · 菜单名」。

### 4.3 结构获取 `fetch_dashboard(qbi, url_or_id, precheck=True)`

1. `resolve_page` 得 pageId。
2. `precheck`:POST `skills/dashboard/handle`(看板权限问题通常在这一步就暴露,如 AE0510200000)。
3. GET `dashboard/query`;非 dict → 协议错误「仪表板结构返回格式异常」。
4. 收集所有组件的 `dataFromId` → POST `dataset/batchGetSchema`(失败吞掉)→ `schema_map = {cubeId: {cubeName, fields}}`。
5. `parse_dashboard(raw, schema_map)` 逐组件(`componentContent` / `queryInput` 是 JSON 字符串,解析失败当 `{}`):
   - `type == "query2"` → 查询控件:`{component_id, fields:[{label, widget, required, default, granularity}]}`;
   - `type == "tab"` → 页签:`{component_id, name, tabs:[标题…]}`;
   - `type == "text"` → 文本组件:去 HTML 标签后的正文(≤500 字)进 `texts`;
   - 其余 → 图表:
     ```
     {component_id, name(attribute.caption 或 componentName), chart_type,
      cube_id(queryInput.sourceId 或 dataFromId), cube_name(schema_map),
      dimensions:[{name, aggregate}], measures:[{name, aggregate}], filters:[字段名],
      position:{x,y,w,h}}
     ```
     字段名优先级:`fieldSettingMap[uuid].aliasName`(且不是 10 位 hex 乱码)> schema 里按 `pathId` 找到的 caption > 列 `caption` > 列 `name`。`area.id == "drill"` 跳过;`area.id == "filters"` 或 `queryAxis == "filter"` 进 filters;`itemType == "measure"` 进 measures,否则 dimensions。
   - `cubes`:按图表出现顺序去重 `{cube_id, cube_name, charts:[图表名]}`,再补 schema 里有但图表没引用的。
   - 输出:`{name, page_id(treeId/pageId/dashboardId), workspace_id, gmt_modified, charts, query_controls, tabs, texts, cubes}`。
6. 补 `view_url`、`portal`、`suggested_questions`(§4.6)。

**真图表判定**(`data_charts` / `is_data_chart`):有 `cube_id` 且 `chart_type` 不匹配
`(container$|^tab$|^tabs$|^text$|^query2$|iframe|^image$|^picture$|^layout|divider|blank)`(忽略大小写)。
注意 `table` / `cross-table` 是真图表,不能被 `tab` 误伤。资产列表的「图表数」只算真图表(`chart_count`),另给 `component_count`。

### 4.4 资产登记 / 刷新 / 可见性

- 登记 `register_dashboard(actor, connection_id, url, name, scenic_id)`:取连接 → `fetch_dashboard` → 按 `(connection_id, 'dashboard', page_id)` 找已有行(有则更新)→ `scenic_id = _bind_scenic(actor, scenic_id)`(景区账号只能绑自己的景区,集团账号任意,留空 = 集团级)→ `name = 传入 or 看板名 or pageId` → `url` 原样 → `meta = 摘要`。
- 刷新 `refresh_asset`:用 `a.url or a.ref_id` 重新登记(门户地址会重新走菜单解析)。
- 预览 `POST /dashboards/parse`:只解析不保存。
- 可见性 `_asset_scope`:集团账号全部;景区账号 = 自己登记的 + 本景区的 + **集团级的(scenic_id 为空)**;`get_asset` 与列表必须同一口径(否则「下拉里选得到、发起时报无权访问」)。停用资产:能看到,用不了,报「数据资产「x」已停用:原因…」。
- 改名 / 改归属 `update_asset`:改同一行(asset_id 不变),同时刷新指向它的问题的 `target_data_name`。**不要让人「删了重登记」改归属**——删掉的那一刻所有指向它的问题失效。
- 远端 id 跨连接不可用:资产 / 文件与本次连接不一致时报错(`_same_connection`),并区分「那条连接还在(切过去即可)」与「已被删除(只能重新登记)」。

### 4.5 问题上的目标数据显示列(`_target_display`)

- `target_data_id`:`page_id` 或 `cube_id`;直接粘贴的地址:看板取 pageId、门户取 **productId**(门户的 pageId 要运行时按菜单解析);有 `asset_id` 时兜底取资产 `ref_id`。
- `target_data_name`:`cube_name` > `asset_name` > `name` > `dashboard`;有资产兜底取资产名。

### 4.6 候选问题(`suggest_questions`,一键采纳成固定问题)

每张有数据集且有度量的图表:`"{图表名}:按{第一个维度}看{前两个度量}的分布"`(无维度则 `"{度量}是多少"`),`capability=dataset_qa, cube_id=图表数据集`,去重,最多 12 条;有图表时再加一条 `"解读这个仪表板的核心指标变化、异常波动和趋势"`(`insight`)。

### 4.7 固定问题里直接新增仪表板 / 门户

TargetPicker 的仪表板模式有两种:
- **select**:下拉选已登记资产;最后一项「＋ 新增仪表板 / 数据门户地址…」(没选连接时禁用)→ 展开内联表单(地址 + 可选显示名)→ 调登记接口(带当前连接、当前问题的景区)→ 成功后**选中新资产**并刷新下拉。这样别的问题也能选到它,并且能按图表范围解读。
- **paste**:直接把地址存进 `target.dashboard`(不登记);可「解析」预览结构。

## 5. 统一执行入口 `run_stream`(逐步规格)

签名:
```python
async def run_stream(actor, *, connection_id, capability, question, target=None, mode="direct",
                     locale=None, session_id=None, fixed_question_id=None, context_question=None,
                     report_async=None, scenic_id=None, use_cache=True, task_id=None) -> AsyncIterator[dict]
```

步骤(顺序即规格,每一步的位置都有原因):

1. **固定问题带出**(给了 `fixed_question_id`):`get_fixed(actor, id)`(按可见范围,新旧 id 都认)。问题原文 = 传入 or `fq.issue`;能力 = 传入 or `fq.capability`;连接 = 传入 or `usable_connection_id(actor, fq.connection_id, scenic_id or fq.scenic_id or actor.scenic_id)`(写死的连接被删 / 停用 / 改绑别的景区时**按景区重新挑一条能用的**);locale;口径说明 `instruction = fq.model_instruction`;target 为空时用 `fq.target`;`scenic_id` 未传且问题挂了景区、且(集团账号 或 就是本景区)时取问题的景区。
2. 问题为空 → 「问题不能为空」。
3. `cache_question = question`(**运行时变量替换前**的原文,缓存按它比);然后 `question = render_runtime_vars(question)`、`instruction = render_runtime_vars(instruction)`。
4. `scenic_id = _bind_scenic(actor, scenic_id)`(景区账号指定别的景区 → Forbidden)。
5. **加速缓存**(§10):`use_cache` 且是固定问题、不是追问、且调用方**没有改写能力 / 目标数据**(`capability != fq.capability` 或 `target != fq.target` 视为改写),问题开了加速 → `cached_run(fq, scenic_id, ttl, cache_question)` 命中则产出回放事件并结束。放在取连接之前:连接断了的空档里预热过的问题仍答得出来(标了 from_cache)。
6. 固定问题且没解析出连接 → 「景区 X 还没有可用的 Quick BI 连接 —— 问题「…」原先绑的那条已被删除或停用…」。
   `connection_id = connection_for_target(actor, target, connection_id)`:**目标数据决定连接**——target 里有资产 / 文件时,用它登记时的那条连接(先确认此人能用那条连接,防借目标数据越权换凭证)。
7. **景区数据集映射**:有景区、能力不是 `dashboard_qa` / `file_qa`、且 target 里没有任何目标数据键(§3.2)→ 取 `tc_qbi_scenic_datasets` 该景区的行,**且映射的连接 == 本次连接**才套用:`target += {cube_id, cube_name, from_scenic_map: True}`。不按名字猜、不挑「默认资产」。
8. 开放平台调用且连接未开放 API → Forbidden。
9. 有 `asset_id` 无 `asset_kind` → 查资产补上。
10. **文档纠正**:目标文件里有非表格文档(pdf / 图片 / doc / ppt…)且能力是 `file_qa` / `insight` → 改为 `doc_parse` 并 `target.doc_then = 原能力`。
11. **能力按目标数据纠正**(目标数据是用户刚显式选的,能力常是上一轮留下的):数据集 + `dashboard_qa`/`report` → `dataset_qa`;仪表板 + `dataset_qa` → `dashboard_qa`。
12. **自动路由**(能力为空 / auto):报告关键词 → `report`;有文档 → `doc_parse`(按 `doc_followup` 定是否接问数 / 解读);解读关键词且有文件 / 仪表板 / 数据集 → `insight`;有文件 → `file_qa`;只有仪表板 → `dashboard_qa`;否则 `dataset_qa`。自动路由每轮先清掉会话里粘着的 `doc_then`。
13. 未知能力 → 报错;报告 `report_async` 写进 `target.wait`;`locale = 传入 or 按问句判断(去掉引号内实体名后含中文 = zh_CN)or 连接默认`。
14. **发给上游的问题** `sent_question`:
    - 追问(有 `context_question`、能力是问数类、且问句像追问)→ `"{上文};追问:{本句}"`;
    - 有口径说明且不在问题里 → 追加 `"\n口径要求:{instruction}"`(**追加不替换**)。
    - `question`(展示 / 落库)保持原样;`raw_question = question` 传给 `_prepare`,供「取数 / 选表」等不该被口径说明带偏的中间步骤用。
15. 建运行记录(`status=running`,target 去掉 `data`,`task_id = 传入 or 任务上下文`)。
16. 产出 `run` 事件(含 run_id、能力、是否路由、连接名、`capability_source`、`sent_question`、景区、target…)。
17. 报告类按连接串行(`report_slot`:同一账号同时只允许一个运行中的报告);`_prepare` 选能力生成器;逐事件:终止标记检查 → 报告事件处理 → **AnswerSplitter** 把混在正文里的思维链切到 reasoning → 累积 + 打通道 + 留痕 → 下发。
18. **成功 / 失败判定**(按顺序):
    - 有 error 且既没回答也没图表 → failed(取最后一个错误);
    - **能力是 `insight` 且解读接口没有给出正文**(`acc.text("answer")` 为空)→ failed,原因取最后一个错误或「取到了数据,但解读没有返回内容」,码 `INSIGHT_EMPTY`;
    - 非报告类、成功但既无回答也无图表也无报告 → failed,码 `EMPTY_RESULT`(文案:常见原因是问题和数据对不上 / 问题里夹了与取数无关的话);
    - QuickBIError → failed(报告已拿到 chatId 且是超时 / 网络类 → 保持 running,后台续跑);输入类错误 → failed(kind=input);其它异常 → `internal`。
19. 收尾 `finalize`:写 answer / result / error / debug / 耗时;固定问题写执行留痕;终止标记优先(避免「点了终止又被成功覆盖」);客户端断开 / 取消也要收尾(非报告 → failed `cancelled`)。`done` 事件带 `content = acc.as_llm_text()`(给模型 / 外部调用方的整段文本)。

`_prepare` 中与仪表板相关的展开:有 `asset_id` → 校验同连接;仪表板资产 → `page_id ← ref_id`、`dashboard_cubes ← meta.cubes`、`asset_name`;数据集资产 → `cube_id ← ref_id`(target 已有 `cube_ids` 时不并入,避免把多选压成单表);`cube_ids` 只有 1 个 → 当 `cube_id`。

## 6. 仪表板问数 `dashboard_qa`

对齐官方「小Q报表技能」。入口 `run_dashboard_qa(qbi, question, dashboard, cube_ids, cube_id, charts, chart_ids, single_cube, locale)`:

1. 给了 `cube_id` → 单表问数,结束。
2. 没有缓存的结构(`charts is None`)且有地址 → 现拉 `fetch_dashboard`,下发 `meta{page_id, dashboard_name, dashboard_cubes}`。
3. 候选数据集 `dashboard_candidate_cubes(charts, chart_ids, fallback)`:所选组件(`chart_ids` 空 = 全部真图表)用到的数据集,按看板顺序去重;都没有 → 退回登记的 `cube_ids`;仍为空 → 「该仪表板(所选组件)没有引用任何数据集,无法问数;可改用「解读」」。
4. `single_cube`(仅 `qa_scope == "dataset"` 的存量配置)→ 在候选里智能选表挑一份(`restrict=True`)。
5. **问题点到图表名** `match_chart_by_question(strip_instruction(question), 所选组件)`:
   - 图表名去空白、去尾部数字序号后,作为子串出现在问题里;取**最长**命中;
   - 无意义的名字不参与:长度 < 2、uuid 开头、「查询 1 / 图表 3 / chart」这类默认名;
   - 命中 → 用这张图的数据集单表问数(流式)。
   - **必须用去掉口径说明的问题匹配**:口径里提一句「参考客流趋势图」就会锁到那张图的数据集。
6. 否则 → **多表问数** `run_multi_cube_qa(候选)`(§6.1)。

### 6.1 多表问数 `run_multi_cube_qa`

- 只有 1 个数据集 → 单表问数。
- 超过 30 个(`MULTI_CUBE_LIMIT`)→ 按问题与数据集名的相关度排序截取前 30(名称拿不到的排后),并提示。
- 请求 `queryByQuestion {userQuestion, userId, multipleCubeIds:[数组]}` → `multi_cube_events` 转事件(§9)。
- **选中的表这一期没数据的兜底**:所有图表的度量列都是空 / 「-」/ None(`chart_has_values` 为假)→ 并发逐个数据集再问一遍(最多 12 个,并发 4),只下发**有值**的图表,每张标上来源数据集(`where_label = "数据集:{名称}"`)。来历:运行 31427b3e 选中「供应商每日报表」昨日一行「-」,同问题逐个取数(027eee3d)能在「销售报表」里取到。

## 7. 仪表板解读 `insight`

### 7.1 数据来源优先级(`_prepare`)

1. `data`(粘贴文本)或上传文件(xls / xlsx / csv 本地转 Markdown)→ 直接解读;
2. 显式给了数据集(`cube_id` / `cube_ids`)→ 数据集解读(§8.1)——哪怕 target 里还残留着 asset_id / page_id;
3. 有仪表板 → **仪表板解读(按图表范围)**`_dashboard_insight` → `run_dashboard_insight`;
4. 都没有 → 「解读需要数据来源:…」。

### 7.2 `run_dashboard_insight` 规格

参数:`question`(带口径说明,给解读)、`page_id`、`charts`(资产缓存的结构;未登记的看板现拉)、`chart_ids`、`fetch_question`(原问题,给补取)、`fetch_missing`(= `target.insight_source != "snapshot"`)。

1. 图表范围:`selected = 真图表 ∩ chart_ids`(空 = 全部);给了 `chart_ids` 却一张都找不到 → 输入错误「所选图表在这块仪表板里都找不到了(看板可能改过),请刷新资产后重新选择」。下发 `meta.chart_scope {mode, selected, total}`。
2. **快照**:`dashboard_snapshot` 轮询(PROCESSING 继续,每次下发进度 status;SUCCESS 取 `resultMarkdownText`,空串 → 「仪表板快照为空…」;FAILED → 带 errorInfo 报错;未知状态 → 协议错误;超过 60 次 → 超时)。
3. `split_snapshot`:按 `## ` 切成 `[(标题, 整段)]`,标题前的零碎内容并入第一段。
4. **空表头不算覆盖**:`section_has_data(段)`——带表格的看有没有数据行(表头、分隔行不算),不带表格的看有没有正文。只有表头的段**丢弃**,并下发「快照里 N 张表只有表头、没有数据行:…」。
5. `match_snapshot(有数据的段, selected)`:先按原名精确匹配,再按「去空白、去尾部数字序号」匹配(快照标题会带序号:「情绪占比4」),一段只用一次。全选时,对不上名字的有数据段也带上(它们也是这块看板的内容)。
6. `missing = selected 中没被覆盖的图表`;涉及的数据集去重 `cubes`。下发「快照覆盖 N 张图表,另有 M 张不在快照里(通常在其它页签)…」。
7. `fetch_missing == False` 且有缺失 → 下发「只用仪表板快照解读(与在仪表板上解读一致),M 张不在快照里的图表未纳入」,不补取。
8. **补取**(有缺失且允许):一次多表取数 `run_multi_cube_qa(build_fetch_question(fetch_question or question, missing), cubes)`:
   - 取数问题 = 原问题(**不带口径说明**)+ 取数要求(附录 B)+ 「需要的字段:…」(缺失图表的维度 + 度量,去重,最多 15 个)+ 「按看板图表的口径列出数据(图表本身是明细就列明细)」;
   - 返回的图表:`has_row_labels` 为假(多行却没有任何一列是文字 / 维值,只有一串数字)→ 不纳入,记名字;否则纳入。图表事件照常下发(用户能在图上对数);
   - 取数阶段的文字只进思考过程(`reasoning`),不当回答;
   - 取数报错 → 记 `fetch_error`,不中断;全失败 → 下发「快照外的数据集取数失败,只用快照里的数据解读:…」。
9. **拼解读底稿**(顺序固定):快照命中段(按图表顺序)→ 快照其余有数据段 → 补取的表(`charts_to_markdown`,§9)。**快照在前**(看板本来的样子),补取在后。
10. `fit_sections`:超过 100,000 字符时逐级压每张表的行数 200 → 100 → 50 → 20 → 10(被压的表注明「本表共 N 行,只列前 K 行」),压到 10 行仍超则原样交给解读、由解读报「数据量过大」。
11. **没有任何数据行**(快照段无数据且补取表都没行)→ 快照里有空表头时报 `SNAPSHOT_EMPTY`(附录 B 全文),否则报「所选图表一张都没有取到数据,无法解读(仪表板可能没有数据,或查询控件必填未设默认值)」。**绝不把空表交给解读。**
12. 调解读 `run_interpretation(question, markdown)`:
    - markdown 为空 → 输入错误;**有表格却没有任何数据行 → `NO_DATA_ROWS`**;超长 → 「数据量过大…」;
    - `userQuestion = INSIGHT_GUARD_PROMPT + question`(附录 B);
    - 回答恰好是「不存在」→ 追加说明「所用数据里没有和这个问题相关的内容。它包含:{表标题…}。请确认问题和所选数据源是同一类数据…」。
13. 结尾说明:补取全失败 → 「看板上另有 M 张图表不在快照里,按问题补取数据失败,本次解读只用了快照里的 N 张」;有未纳入的无维值表 → 「快照外补取的 K 张表只有数值、没有对应的名称(维值),未纳入解读:…」。

### 7.3 「只用仪表板快照」开关

- target `insight_source = "snapshot"`;问题配置里能力 = 解读、目标 = 仪表板时显示复选框「只用仪表板快照(与在 Quick BI 仪表板上点「解读」一致)」。
- 语义:与官方 skill / 在仪表板上点解读同一份底稿,不补取其它页签。快照为空表头时直接 `SNAPSHOT_EMPTY`。

## 8. 数据集解读、报告引用仪表板数据

### 8.1 数据集解读 `run_dataset_insight(question, cube_id, cube_ids, restrict, locale, fetch_question)`

1. 取数问题 = `build_fetch_question(strip_instruction(fetch_question or question), [])`(只有取数要求,没有「看板口径」那句和字段清单)。
2. 多选(无 cube_id 且 ≥2)→ 多表问数;否则单表 / 智能选表。
3. 取数事件:图表下发并收集;文字进思考;**error 不下发,记下**。
4. 取数报错且一张图都没有 → 失败「从数据集取数失败:…」;报错但有部分图表 → 提示后用已取到的解读。
5. 没有任何有值图表(`chart_has_values` 全假,包括全是「-」)→ 失败「按这个问题在数据集里没有取到数据,无法解读…」。
6. `charts_to_markdown` → 解读(用带口径说明的 `question`)。

### 8.2 报告引用仪表板数据

- `use_dashboard_data`(默认真)且有仪表板 → 快照 → **整份快照都没有数据行 → `SNAPSHOT_EMPTY`**(不上传空 CSV、不发起报告)→ `markdown_to_csv_files` 只取**有数据行**的表、最多 5 张 → `uploadReferenceFile` → 发起报告。
- `attachment.useOnlineSearch` 跟随 `web_search`(以前写死 True,关不掉联网)。
- 报告按连接串行;创建即返回时由后台 `report_watcher` 续跑收尾。

## 9. 多步结果与图表标题规则

小Q 常把一个问题拆成多条查询(按数据域拆 5 条 SQL 之类)。规则:

1. **图表标题不带口径 / 取数要求**:`display_question(q)` = 去掉 `"\n口径要求:"` / `"\n(取数要求:"` 之后的内容;追问形式 `"上文;追问:本句"` 只留本句。流式问数的 `DatasetQaNormalizer` 用它做标题;`strip_instruction(q)`(只去口径 / 取数要求、保留追问上文)用于**选表与图表名匹配**。
2. **每张表的查询条件** `where_label`:从该步 DSL(`param` 事件里的 `info.abstractDsl`,或多表结果每步的 `info`)的 `where` 生成,如 `时间类型=week · 数据域=OTA直销`。兼容两种 DSL 形状:`{column:{name}, operator, value}` 与 `{col:{n}, op, v}`;操作符映射 eq `=`、ne `≠`、gt `>`、ge/gte `≥`、lt `<`、le/lte `≤`、in `∈`、not_in `∉`、like/contain `含`、between `介于`;列表值用「、」连接。
3. `multi_cube_events`:单步用顶层;多步用 `dataList`(元素可能是 JSON 字符串)。标题 = `display_question` 或「查询结果」,多步加「(i)」。**多步里 0 行的那一步保留**(解读据此知道「这块查过、没数」);单步 0 行不出图。结论 = 顶层 `conclusionText`,没有则拼各步(含第 1 步)的结论;既无有值图表又无结论 → 「在所选数据集里没有查到和这个问题相关的数据…」。
4. `charts_to_markdown`(给解读的底稿):
   - 几张表标题相同 → 用 `where_label` 当表名(没有则「查询结果 i」);标题不重复保持原样;
   - **0 行的表保留一段**:`## {表名}\n\n(本次查询没有返回数据:这个条件下没有数据)`——直接丢掉的话解读会拿别的表的数去填这一块;
   - 每表最多 500 行,超出注明。
5. `as_llm_text`(给 Agent 工具 / 外部调用方):标题后附 `(where_label)`;0 行写「(这个条件下没有数据)」;最多 5 张,超出写「(另有 N 张表未列出)」;每表最多 30 行(工具可配)。
6. 前端结果页:图表标题下一行显示 `where_label`。

## 10. 加速缓存(预热)规范

### 10.1 原则

- **只有一套缓存**:`service.cached_run` + `_replay_events`,由 `run_stream` 统一判断。APP、管理端、开放平台、Agent 工具、预热任务都不许另写回放逻辑(APP 曾有一套 12 小时回放,不看开关 / 不看清除,已删除)。
- 缓存 = `tc_qbi_runs` 中满足条件的最近一次成功运行,没有缓存表。

### 10.2 命中条件 `cached_run(issue, scenic_id, ttl_minutes, question)`

全部满足才命中:
1. `fixed_question_id ∈ {issue_id, source_question_id}`;
2. `status = 'success'`;
3. `created_at >= now - ttl`;
4. **问题文本**:原文含运行时变量(`{{截止时间}}` 等)→ 按 LIKE 比,变量处是 `%`,其余逐字(`\ % _` 转义,`escape='\'`);否则逐字相等。传入的是**运行时变量替换前**的原文、参数模板**已展开**的文本(`{{month}}` 填 8 月和 7 月是两个问题);
5. `created_at > issue.qbi_cache_cleared_at`(清过缓存时);
6. 景区:有景区 → `scenic_id` 相等;集团级 → `scenic_id IS NULL`(不能把 A 景区的结果给 B,也不能把某景区的当集团级);
7. **景区数据集映射改过**:运行的 `target.from_scenic_map` 为真且 `created_at <= 映射.updated_at` → 跳过这条(取最近 5 条依次判)。

不读缓存的情况:`use_cache=False`(预热任务、「立即加速」、管理台运行 / 重新问、操练台 `/run` 默认)、追问、调用方改写了能力 / 目标数据、问题没开加速。

### 10.3 回放事件(`_replay_events`)

与真跑同形,全部打上通道:
```
run{run_id, capability, label, capability_source:"prewarm", sent_question, from_cache:true, cached_at}
status{stage:"cache", message:"直接呈现加速结果(生成于 …)"}
chart{chart} × N            # result.charts
text{section:"answer", delta: answer}
report{report_url, chat_id, finished:true, success:true}   # 有报告时
done{run_id, status:"success", answer, chart_count, usage, trace_id, from_cache:true, cached_at, result,
     content: as_llm_text()}
```
以前回放 `{"type":"answer"}`:没有任何下游认——Agent 工具拿到 ok=True 却是空内容,APP 一片空白,操练台没有图表。

### 10.4 缓存作废(`qbi_cache_cleared_at`)

刷成当前时间的时机:
1. 管理端保存固定问题(`save_fixed`)或问题管理保存(`issue_service.update_issue`)时,以下任一字段变化:`issue, connection_id, capability, target, locale, model_instruction, scenic_id`(问题管理另含 `param_template`)。排序、标签、上下架不清。
2. 管理台「运行 / 重新问」(`POST /fixed-questions/{id}/run`,默认 `use_cache=false`):**先清再跑**——就算这次失败,APP 也不会再回放旧答案。但只有**能管这条问题的账号**才清(`can_clear_cache`:集团账号;或问题属于本景区);景区账号重问集团级问题只是本次不读缓存,不替别的景区清。
3. 行菜单「清除缓存」(`POST /fixed-questions/{id}/clear-cache`):同样的权限;无权 → 「这条问题是集团级(所有景区共用)或属于其他景区,它的缓存只能由集团账号清除」。只读角色不能清。
4. 景区数据集映射变化:不改问题行,在命中判断里按映射 `updated_at` 过滤(§10.2-7)。

运行记录本身不删(审计 / 排障底账)。

### 10.5 预热任务(`cronjobs/quickbi_prewarm.py`)

- 注册在 cron 心跳(5 分钟一拍)上;每轮最多 20 条,串行,单条超时 10 分钟,失败不重试(下一轮自然再轮到),幂等。
- 选题:开了加速、上架的 Quick BI 问题;有景区的问题只跑它的景区;**集团级问题只跑最近「存储时长 × 24」内真有人问过的景区**;景区数据集映射上关了预热的景区跳过。
- 是否需要跑:**用与回放同一个判断** `cached_run(row, scenic_id, interval, 展开后的问题)`——刷新间隔内已有可回放的成功运行就跳过。各判各的会出现「预热以为有、回放却用不上」的空窗。
- 发出去的问题:`expand_params(row, "")`(展开 `{{month}}` 等与参数模板),不能原样发 `row.issue`。
- 用系统身份(问题所有者 / cron,super_admin)、`use_cache=False`、报告类创建即返回。

## 11. APP 入口规格

### 11.1 `POST /api/app/chat`(带 issue_id / question_id 的 Quick BI 问题)

1. 解析问题行:issue_id → question_id → 问题原文匹配(`match_issue_by_text`,本景区 + 集团级)。(原「【主题解读】xx」原文兜底已删除。)

   - 连接:`connection_usable(issue.connection_id, ask_scenic)`(写死的连接不可用则按景区重挑);没有 → 「景区 X 还没有可用的 Quick BI 连接…」。

## 附录 B · 提示词 / 规则常量原文

**解读守卫提示词** `INSIGHT_GUARD_PROMPT`(拼在问题前):
> 【关键要求】:若输入数据中未包含用户提问的相关内容,则直接回复“不存在”,禁止随意捏造数据。若报告中包含相关数据,且用户问题有明确指向,则须在报告开头设置“用户问题解答”章节,针对问题作出直接、明确的回答,并予以标注。

**取数要求** `FETCH_DETAIL_RULE`:
> 取数要求:表里有统计日期 / 分区日期这类字段时,只取最新的那一个日期,不要把不同日期的值加在一起;比率、百分比、得分、环比、同比这类指标不能相加。

**仪表板补取问题** `build_fetch_question(question, charts)`:
```
{原问题(不带口径说明)}
(取数要求:按看板图表的口径列出数据(图表本身是明细就列明细);表里有统计日期 / 分区日期这类字段时,只取最新的那一个日期,不要把不同日期的值加在一起;比率、百分比、得分、环比、同比这类指标不能相加。需要的字段:{字段1、字段2…(≤15)}。)
```
数据集解读时 `charts` 为空:没有「按看板图表的口径…」与「需要的字段」。

**快照全空** `SNAPSHOT_EMPTY`:
> 仪表板快照取回的 {N} 张表({表名…})都只有表头、没有任何数据行,无法解读。快照是用这条连接的 Quick BI 账号(user_token 对应的用户)、按看板查询控件的默认值导出的,常见原因:① 这个账号在看板上没有数据权限(行级权限)—— 你用自己的账号在 Quick BI 里能看到数,不代表它能看到;② 查询控件(日期 / 景区等)没有默认值,或默认日期当天的数据还没产出;③ 看板此刻本身就是空的。请用这条连接对应的账号登录 Quick BI 打开这块看板,确认不做任何筛选时能看到数据。

**「不存在」补充说明**:
> 所用数据里没有和这个问题相关的内容。它包含:{表标题…}。请确认问题和所选数据源是同一类数据(比如票务问题要配票务看板 / 数据集),或换一个数据源再试。

**发给上游的问题拼接**:`"{上文};追问:{本句}"`、`"{问题}\n口径要求:{口径说明}"`。
